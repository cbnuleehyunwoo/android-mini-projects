| **선택 기술: iOS Native** | OS 앱은 Swift와 SwiftUI를 기반으로 개발한다.네이티브를 선택한 이유는 다음과 같다.<br/>첫째, 러닝 앱 특성상 백그라운드 위치 추적이 중요하다. iOS 네이티브 환경에서는 CoreLocation, Background Modes 등을 직접 제어할 수 있어 백그라운드 상태에서도 비교적 안정적인 러닝 기록 수집이 가능하다.<br/>둘째, 배터리 최적화 측면에서 유리하다. 러닝 앱은 장시간 GPS와 센서를 사용하는 서비스이기 때문에, 불필요한 연산과 위치 업데이트를 줄이고 OS 수준의 최적화 기능을 직접 활용할 수 있는 네이티브 방식이 적합하다.<br/>셋째, HealthKit, Live Activity, Dynamic Island 등 iOS 생태계 기능을 활용하기 쉽다. 향후 사용자의 운동 기록, 심박수, 칼로리 등의 건강 데이터를 연동하거나 러닝 중 실시간 정보를 잠금화면에 표시하는 기능을 확장하기에도 네이티브가 유리하다. |

### 선택하지 않은 옵션

| 후보 | 검토했지만 선택하지 않은 이유 |
| --- | --- |
| **Flutter** | Flutter는 하나의 코드베이스로 iOS와 Android 앱을 동시에 개발할 수 있다는 장점이 있다. 개발 속도가 빠르고, 패키지 생태계도 잘 갖춰져 있으며, 두 플랫폼에서 거의 동일한 UI를 제공할 수 있다. 하지만 러닝 앱의 핵심 기능인 백그라운드 GPS, HealthKit, Apple Watch 연동, 배터리 최적화 영역에서는 결국 네이티브 코드 작성이 필요하다. 또한 Flutter 앱은 네이티브 앱에 비해 앱 크기가 크고, 백그라운드 작업이나 센서 기반 기능을 세밀하게 최적화하는 데 한계가 있을 수 있다.따라서 빠른 화면 개발에는 장점이 있지만, 본 프로젝트의 MVP 핵심 기능과는 우선순위가 맞지 않아 선택하지 않았다. |
| **React Native** | React Native는 AI 코드 생성 도구와의 궁합이 좋고, JavaScript/TypeScript 기반으로 빠르게 개발할 수 있다는 장점이 있다.하지만 네이티브 기능 연동이 복잡해질수록 브릿지 관리, 라이브러리 버전 충돌, iOS/Android 빌드 환경 관리의 부담이 커질 수 있다. 특히 러닝 앱처럼 위치, 센서, 워치, 백그라운드 실행 기능이 중요한 서비스에서는 안정성 측면에서 부담이 있다.따라서 초기 MVP의 안정성을 우선하기 위해 선택하지 않았다. |
| **KMP / CMP** | Kotlin Multiplatform과 Compose Multiplatform은 비즈니스 로직을 공유하고, Kotlin 기반으로 Android와 iOS를 함께 개발할 수 있다는 장점이 있다. 특히 Android 개발 경험이 있는 팀에게는 매력적인 선택지다.하지만 iOS 앱의 완성도, Apple Watch 연동, HealthKit 활용 측면에서는 여전히 Swift 기반 네이티브 개발이 필요하다. 또한 Compose Multiplatform의 iOS 생태계는 Flutter나 네이티브에 비해 아직 성숙도가 낮고, 자료와 레퍼런스도 상대적으로 부족하다.따라서 이번 MVP에서는 기술 검증 비용을 줄이고 iOS 핵심 기능 구현에 집중하기 위해 선택하지 않았다. |

## B. 회고

### **가장 어려웠던 의사결정**

**크로스플랫폼(Flutter, RN) vs iOS 네이티브** 중 어떤 기술을 선택할 것인지가 가장 어려운 의사결정이었습니다.

초기에는 Flutter 또는 React Native를 활용하여 iOS와 Android를 동시에 대응하는 방향을 검토했습니다. 하지만 논의를 거치며 다음 두 가지 이유로 **iOS 네이티브 개발**을 선택했습니다.

1. **네이티브 의존도가 높은 서비스 특성** 러닝 앱의 핵심 기능(백그라운드 GPS 추적, 가속도계 기반 부정 이동 감지, Apple Watch 연동 등)은 모두 네이티브 API에 의존합니다. 크로스플랫폼을 도입하더라도 결국 주요 로직은 네이티브 코드로 작성해야 하므로, 실질적으로 공유되는 부분은 UI에 한정됩니다. UI 공유만을 위해 크로스플랫폼 레이어를 추가하는 것은 오히려 복잡도를 높이고, 백그라운드 배터리 최적화에도 불리하다고 판단했습니다.
2. **4주라는 제한된 개발 기간** 두 플랫폼을 동시에 개발하기보다, 하나의 플랫폼에서 MVP를 확실하게 완성하는 것이 기술 검증과 사용자 경험 검증 모두에 효과적이라고 판단했습니다.

결론적으로, "멀티플랫폼 대응"이라는 확장성보다 **"핵심 기능의 완성도"와 "개발 집중도"** 를 우선하여 iOS 네이티브를 선택했습니다.
